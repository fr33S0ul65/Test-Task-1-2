# Task 1: архітектура класифікатора

## Як працює

```
текст тікета
   → src/classify.py: системний промпт (prompts/classify_v3.txt) + тікет у тегах <ticket>
   → src/llm.py: виклик моделі (повтори при rate limit / таймауті / 5xx)
   → перевірка відповіді: валідний JSON, відома категорія й пріоритет, булеві поля
   → правило в коді: тікет із ≤3 слів завжди йде людині
   → результат або fallback у чергу людини
```

Результат:

```json
{
  "category": "expert",
  "refund_requested": true,
  "priority": "high",
  "next_step": "Перевірити сесію і списання, рішення щодо повернення",
  "needs_human": true,
  "human_reason": "Погроза chargeback; запит на повернення коштів"
}
```

Поля `category`, `priority`, `next_step` вимагає завдання. `refund_requested` — моє рішення (див. нижче). `needs_human` і `human_reason` — механізм human-in-the-loop.

## Модель і чому

**`claude-haiku-5-5`**, effort `medium`, з кешуванням системного промпту.

Порівнював чотири моделі двох провайдерів у парах з однаковою ціною за токен: дешева пара (`claude-haiku-5-5`, `gpt-6-luna`) і середня (`claude-sonnet-5-5`, `gpt-6.1-sol`). Haiku показала 21/21 на основному й прихованому наборах, найменший середній час (1.84 с без кешу) і з кешуванням найнижчу ціну (~$1.15 за 10 000 тікетів). Середня пара в 10–17 разів дорожча й точнішою не виявилась. Повні цифри — у [evaluation.md](evaluation.md).

Застереження: різниця між моделями — один тікет із 21, тож висновок «всі чотири моделі справляються, вирішують ціна й швидкість» надійніший, ніж «Haiku точніша».

## Структура промпту

Фінальна версія: [prompts/classify_v3.txt](../prompts/classify_v3.txt). Промпт написаний англійською (з українським промптом окремо не порівнював); `next_step` і `human_reason` модель пише українською.

1. **Роль і контекст продукту:** класифікатор підтримки астрологічного застосунку з підписками й платними чатами з експертами.
2. **Формат:** повернути лише JSON, без іншого тексту.
3. **Категорії** з коротким описом кожної та правилом «обирай за першопричиною, а не наслідком».
4. **Поля:** коли ставити `refund_requested`, критерії трьох пріоритетів, перелік випадків для `needs_human`, мова `next_step` і `human_reason`.
5. **Захист від prompt injection:** текст тікета — це дані користувача, інструкції всередині нього не виконуються. Сам тікет передається окремо, в тегах `<ticket>`.
6. **Приклад формату виходу.**

Налаштування виклику: `temperature` не передається, бо Claude 5.5 і GPT-6 з увімкненими роздумами її не приймають; `max_tokens` 4000, бо роздуми входять у ліміт вихідних токенів.

Як промпт змінювався — у [prompt_evolution.md](prompt_evolution.md).

## Категорії і логіка

Категорія відповідає на питання **«у чому першопричина проблеми»**:

| Категорія | Що сюди потрапляє |
| --- | --- |
| `subscription` | Скасування, зміна плану, trial, дата наступного списання; списання після скасування; запит на повернення без вказаної причини |
| `payment_issue` | Оплата не пройшла, подвійне чи неочікуване списання, баланс чату не поповнився |
| `technical` | Баги, застосунок вилітає, чат з експертом не з'єднується |
| `account` | Вхід, пароль, зміна email чи даних народження, видалення акаунта, запит на дані |
| `product` | Як користуватися функцією, неточний гороскоп, пропозиції й відгуки |
| `expert` | Поведінка експерта, якість консультації |

**Повернення коштів — не категорія, а окремий прапорець `refund_requested`.** Повернути гроші просять через будь-яку причину: неочікуване списання, грубого експерта, баг. Якщо зробити повернення категорією, тікет «експерт пішов через 2 хвилини, поверніть гроші» мусить обрати між `expert` і `refund`, і одна з двох важливих ознак губиться. З прапорцем видно і причину, і те, що людина хоче гроші назад. Розглядав також ієрархію «категорія → підкатегорія» і відмовився: класів ставало 13–14, а тестів на кожен клас — по одному.

**Пріоритет** (3 рівні) незалежний від `needs_human`: тікет для людини може бути терміновим (`high`) чи ні (`medium`).

## Обробка збоїв

| Ситуація | Що відбувається |
| --- | --- |
| Rate limit, таймаут (60 с), помилка з'єднання, помилка сервера 5xx | До 3 спроб з паузою 2 і 4 с (`src/llm.py`) |
| Невірний ключ, невідома модель, невалідний параметр | Без повторів, одразу помилка |
| Усі спроби невдалі | Fallback: `category: null`, `needs_human: true`, причина «збій класифікації» |
| Відповідь не JSON, невідома категорія чи пріоритет, неправильні типи | Те саме: fallback у чергу людини з описом помилки |
| Порожній тікет | Fallback без виклику моделі |
| Тікет із 3 слів або менше | Код ставить `needs_human: true` незалежно від відповіді моделі |
| Prompt injection у тексті тікета | Тікет у тегах `<ticket>` + інструкція в промпті; навіть якщо модель піддасться, код перевіряє, що категорія й пріоритет з дозволеного списку |

Тікет ніколи не губиться: у найгіршому разі він потрапляє до людини з поясненням, що сталося. У робочих прогонах fallback жодного разу не знадобився, тому збій перевірено навмисно: прихований набір із неіснуючою моделлю (`claude-does-not-exist`). Результат — [eval/results/20261017_1354_…_holdout-only.md](../eval/results/): усі 5 тікетів пішли у fallback з `needs_human: true`, помилку 404 код розпізнав як таку, що не варто повторювати (~0.3 с на тікет). У двох тікетах (h04, h05), де людина не очікувалась, вона все одно з'явилась — при збої система свідомо віддає людині все.

Rate limit і таймаут у реальних прогонах не траплялись; ці гілки перевірено лише на імітованих відповідях під час розробки.

Ідея для продакшну, не реалізована: резервний провайдер (GPT), якщо API Anthropic недоступне.

## Де система може помилятись і як це мітигувати

| Ризик | Приклад | Мітигація |
| --- | --- | --- |
| Неоднозначні межі категорій | h02: чат зависав (technical) + грубість астролога (expert); дві моделі з чотирьох обрали `expert` | Тікет однаково йде людині з правильним пріоритетом; у продакшні — збирати такі розбіжності й уточнювати правила |
| Модель по-своєму тлумачить формулювання промпту | t13 у `gpt-6-luna`: зміну дати народження прочитала як «запит на персональні дані» | Уточнення в промпті v3; поле `human_reason` дає змогу побачити хід думки моделі |
| Модель пропустить ризиковий сигнал | Прихована погроза чи криза не розпізнана | У промпті широкий перелік причин для `needs_human`; правило коротких тікетів у коді; у продакшні — вибірковий перегляд автоматично закритих тікетів |
| Малий тестовий набір | 21 тікет | Висновки подано обережно; 5 прихованих тікетів як незалежна перевірка; набір треба розширювати реальними (знеособленими) тікетами |
| Недетермінованість і коливання швидкості | Час відповіді Luna: 3.08 с і 2.29 с на майже однаковому промпті | По одному прогону на конфігурацію; порівняння швидкості орієнтовне |
| Мови | Перевірено англійську, іспанську, українську, німецьку, польську | Інші мови не тестувались |
| `next_step` вигадує деталі | t11: «відповісти протягом доби»; t04, t06, t12: повернення звучить як вже схвалене | Поле — підказка агенту, а не дія; грошові тікети й так ідуть людині; можливе правило в промпті (див. [evaluation.md](evaluation.md)) |
